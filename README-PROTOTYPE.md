# อิ่มใจ — เว็บไซต์สั่งอาหารล่วงหน้าในวิทยาลัย

Phase 1–6 สร้างด้วย Next.js App Router + React + TypeScript + Tailwind CSS ใช้ JavaScript ES modules (`.mjs`) สำหรับไฟล์ตั้งค่าและสคริปต์ preview

## เริ่มต้นใช้งาน

ใช้ Node.js 24 LTS และ npm จากนั้นเปิด Terminal ในโฟลเดอร์โปรเจกต์:

```sh
npm ci
npm run dev
```

เปิด http://127.0.0.1:3000 ในเบราว์เซอร์ ไม่ใช้การดับเบิลคลิกเปิด `index.html` เนื่องจากโปรเจกต์ใช้ routing และ assets ของ Next.js

## ตรวจสอบและ build

```sh
npm run typecheck
npm test
npm run build
npm start
```

`npm run build` ใช้ Webpack และสร้าง static export ใน `out/` ส่วน `npm start` เสิร์ฟไฟล์ที่ build แล้วด้วย static preview server ที่แนบมา เนื่องจาก `output: 'export'` ไม่ใช้ `next start` เปลี่ยนพอร์ตได้ด้วยตัวแปร `PORT` ทั้ง dev และ build เลือก Webpack เพราะ Turbopack เริ่มกระบวนการ CSS บนเครื่องทดสอบนี้ไม่สำเร็จ

แนบ `out/` ที่ build แล้วมาด้วย จึงทดลองแบบ production ได้ทันทีด้วย `npm start` โดยมี Node.js ติดตั้งอยู่

หาก Windows แจ้ง `EPERM ... mkdir ... .segments` หลัง compile ผ่านแล้ว ให้รัน `npm run build:recover` เพื่อเตรียมโฟลเดอร์ prerender แล้วทำขั้น generate ต่อด้วย CLI ของ Next.js ใช้วิธีนี้เฉพาะหลัง build จากซอร์สเดียวกันล้มเหลวในขั้นสร้างโฟลเดอร์ ไม่ใช้หลังแก้ไขซอร์สโดยยังไม่ได้ compile ใหม่ Phase 2 build ชุดสุดท้ายด้วย Webpack ผ่านโดยไม่ต้อง recovery

## สิ่งที่ทำได้ใน Phase 1

- หน้าแรก ค้นหาชื่อร้านหรือเมนู กรองหมวดอาหารและร้านที่เปิด
- หน้าร้านแยก URL `/restaurants/[id]/` พร้อมเวลารับตัวอย่างและรายการเมนู
- รายละเอียดอาหาร ตัวเลือกเพิ่มเติม จำนวน และราคา
- ตะกร้ากลางด้วย React Context + reducer เพิ่ม ลด ลบ และจำไว้ใน localStorage
- ขอคำยืนยันก่อนเปลี่ยนร้าน จำกัดหนึ่งร้านต่อออเดอร์
- ตรวจจำนวนคงเหลือรวมทุกตัวเลือกของเมนูเดียวกัน
- เมนูหมดและร้านปิดสั่งไม่ได้
- สถานะโหลดหน้า โหลดภาพ ภาพล้มเหลวและลองใหม่ ค้นหาไม่พบ ข้อผิดพลาด และแจ้งทำรายการสำเร็จ
- รองรับมือถือ แท็บเล็ต และคอมพิวเตอร์ มีตะกร้าบนมือถือและ navigation ด้านล่าง
- โครงร่างนำทางร้านอาหารและแอดมิน พร้อมหน้าอธิบายงานใน Phase ถัดไป

## สิ่งที่เพิ่มใน Phase 2

- สมัครสมาชิก เข้าสู่ระบบ และปุ่มใช้บัญชีนักศึกษาตัวอย่าง
- โปรไฟล์ แก้ชื่อและเบอร์โทร เปลี่ยนรหัสผ่าน และออกจากระบบ
- ลืมรหัสผ่านพร้อมลิงก์ reset ทดลองที่ใช้ครั้งเดียวและหมดอายุใน 15 นาที ไม่มีการส่งอีเมลจริง
- หน้ายืนยันออเดอร์ เลือกวันที่และเวลารับ โดยช่วงเต็มหรือเวลาที่ผ่านไปแล้วเลือกไม่ได้
- สรุปเมนู ตัวเลือก ยอดรวม เบอร์โทร และหมายเหตุถึงร้าน
- สร้างออเดอร์ตัวอย่างจากตะกร้า ตรวจจำนวนคงเหลือรวมออเดอร์ในวันเดียวกัน
- หน้าชำระเงินพร้อมเลขออเดอร์ QR สาธิต บัญชีตัวอย่าง และนับเวลาส่งสลิปเริ่มต้น 10 นาที
- แนบ JPG/PNG/WebP ไม่เกิน 5 MB ดูตัวอย่าง เปลี่ยนรูปก่อนส่ง และเก็บประวัติหลังส่ง
- เก็บภาพสลิปใน IndexedDB ส่วน metadata ของบัญชีและออเดอร์อยู่ใน localStorage
- ยกเลิกเมื่อยังไม่ส่งสลิปและหมดเวลา ส่วนออเดอร์ที่ส่งแล้วไม่หมดอายุเพราะร้านตรวจช้า
- รายการออเดอร์ กรองสถานะ รายละเอียด Timeline ประวัติการชำระเงิน และรหัสรับอาหาร
- เพิ่มตัวอย่างสถานะพร้อมรับ รับแล้ว และภาพสลิปมีปัญหาผ่านปุ่มในหน้าออเดอร์
- ตั้งเวลาส่งสลิปสำหรับออเดอร์ใหม่ได้ที่โปรไฟล์ ตั้งแต่ 1–30 นาที

### ทดลองเส้นทางหลัก

1. เลือกอาหารและเพิ่มลงตะกร้า แล้วกดไปเลือกเวลารับ
2. เข้าสู่ระบบด้วยปุ่ม “ใช้บัญชีนักศึกษาตัวอย่าง” หรือสมัครข้อมูลทดลอง
3. เลือกวันที่และเวลาที่ยังว่าง กรอกเบอร์โทร แล้วกดยืนยัน
4. ใช้รูปอาหารที่แนบใน `public/images/` เป็นสลิปทดสอบแทนข้อมูลส่วนตัว เลือกรูปและกดส่งตรวจ
5. เปิดออเดอร์ของฉัน จะพบสถานะ “รอตรวจสอบการชำระเงิน” และประวัติภาพที่ส่ง
6. ทดสอบหมดเวลาโดยตั้งเวลา 1 นาทีในโปรไฟล์ก่อนสร้างออเดอร์ใหม่ จากนั้นไม่ส่งสลิป

QR และบัญชีรับเงินทั้งหมดเป็นข้อมูลสาธิต ห้ามใช้โอนเงินจริง การยืนยันเงินและเปลี่ยนเป็นกำลังเตรียมอาหารเป็นงานของร้านใน Phase 3

## ขอบเขต

ทั้งหมดเป็นข้อมูลจำลอง ออเดอร์และบัญชีใช้งานภายในเบราว์เซอร์นี้เท่านั้น ไม่มีการชำระเงิน ตรวจสลิป AI แชท หรือธุรกรรมธนาคารจริง

- Phase 2: บัญชีลูกค้า เลือกเวลารับ ยืนยันออเดอร์ และส่งสลิป (สร้างแล้ว)
- Phase 3: ร้านตรวจเงินจริงและจัดการอาหาร
- Phase 4: แชท เปลี่ยนเมนู และคืนเงิน
- Phase 5: สมัครร้านและระบบแอดมิน
- Phase 6: เชื่อมและตรวจครบทุกเส้นทาง

บัญชีต้นแบบใช้ PBKDF2 hash รหัสผ่านในเบราว์เซอร์ และเก็บ session ในแท็บ ไม่มี backend หรือระบบสิทธิ์สำหรับ production จึงควรใช้ข้อมูลและรหัสผ่านทดลองเท่านั้น ไม่รองรับการซิงก์ข้ามเครื่อง การล้างข้อมูลเว็บไซต์จะทำให้บัญชี ออเดอร์ และสลิปทดลองหายไป

## Phase 3 — ร้านอาหาร
เปิด /merchant/ เพื่อเลือกร้านจำลอง จัดการออเดอร์ เมนู ช่วงเวลา และตั้งค่าร้าน
- ทุกครั้งที่เปิดตรวจเงิน ต้องรับทราบคำเตือนก่อน การรับทราบไม่เปลี่ยนสถานะ
- ผลอ่านภาพ 3 แบบเป็นการจำลอง ไม่มี OCR หรือการตรวจธนาคารจริง
- ร้านต้องยืนยันตรวจเงินเอง ก่อนเตรียมอาหาร แล้วพร้อมรับ และตรวจรหัสก่อนรับแล้ว
- แจ้งปัญหาพร้อมเหตุผล ลูกค้าเห็นเหตุผลและส่งสลิปใหม่ได้
- เพิ่ม/แก้เมนู รูป ตัวเลือก ราคา จำนวนต่อวัน และเปิด–ปิดเมนู
- ตั้งเวลาเปิดรับและความจุต่อช่วง ลูกค้าเลือกช่วงที่เต็มไม่ได้
- ออเดอร์ซิงก์ข้ามแท็บของเว็บไซต์เดียวกันในเบราว์เซอร์เดียว ไม่ซิงก์ข้ามเครื่อง
- บัญชีและสิทธิ์ยังเป็นต้นแบบ เลือกร้านได้เพื่อทดสอบ ไม่ใช้กับข้อมูลจริง
- แชท เปลี่ยนเมนู และคืนเงินเป็น Phase 4
ตรวจ TypeScript, unit tests 17 กรณี และ production build แล้ว เครื่องมือควบคุมเบราว์เซอร์ไม่พร้อมในเซสชันนี้ จึงยังไม่ได้ตรวจหน้าตา Phase 3 ด้วย browser automation


## Phase 4 — แชท เปลี่ยนเมนู และคืนเงิน (พร้อมทดลอง)
- ลูกค้าเปิดแชทจากรายละเอียดออเดอร์ ร้านเปิดจากแท็บแชทหรือส่วนจัดการออเดอร์
- ส่งข้อความและรูป JPG/PNG/WebP ไม่เกิน 5 MB แสดงเวลาและจำนวนข้อความใหม่ มีตัวจำลองส่งล้มเหลวและลองใหม่
- บทสนทนาไม่เปลี่ยนสถานะออเดอร์หรือการเงิน
- ร้านเสนอเปลี่ยนเมนูได้หลังยืนยันเงินและกำลังเตรียม ลูกค้าต้องยอมรับก่อนเปลี่ยนรายการจริง สามารถปฏิเสธได้
- ส่วนต่างเพิ่มต้องบันทึกตรวจรับเงินเอง ส่วนต่างลดต้องบันทึกคืนเงินก่อนพร้อมรับ
- คืนเงินแยกรอตกลงกับลูกค้า รอคืนเงิน และคืนเงินแล้ว ร้านต้องแนบหลักฐานและยืนยันว่าดำเนินการเอง
- ไม่คืนเงินอัตโนมัติ ไม่โอนเงิน และไม่เชื่อมธนาคารจริง
- ทุกบทบาทยังจำลองในเบราว์เซอร์และเว็บไซต์เดียวกัน สิทธิ์ production และซิงก์ข้ามเครื่องยังไม่มี
- ทดสอบรวม 22 กรณี ตรวจ TypeScript และ production build 20 หน้าแล้ว ยังไม่ได้ตรวจการกด UI ผ่านเบราว์เซอร์ในเซสชันนี้


## Phase 5 — สมัครร้านและระบบแอดมิน (พร้อมทดลอง)
- สมัครร้านด้วยบัญชีตัวอย่าง พร้อมข้อมูลเจ้าของร้านและข้อมูลรับเงินทดลอง ดูสถานะและเหตุผล ส่งแก้ไขกลับได้โดยเก็บประวัติเดิม
- ร้านรอตรวจไม่แสดงในหน้าลูกค้าและเปิดขายไม่ได้ หลังอนุมัติจึงเตรียมเมนูและเปิดรับออเดอร์ได้ ร้านใหม่ใช้เส้นทาง /store/?id=... รองรับ static export
- แอดมินมีภาพรวม คำขอร้าน ผู้ใช้และร้านค้า ออเดอร์และปัญหา และจัดการสิทธิ์ ระงับ/คืนสถานะต้องมีเหตุผล
- แบ่งสิทธิ์อนุมัติร้าน จัดการบัญชี ตรวจออเดอร์ ดูเบอร์โทร ดูสลิป ดูแชท และจัดการแอดมิน แอดมินไม่มีปุ่มยืนยันเงินแทนร้าน
- คำเชิญแอดมินสาธิตมีอายุ 24 ชั่วโมง ใช้ได้ครั้งเดียว ไม่มีส่งอีเมลจริง ป้องกันปิดผู้จัดการสิทธิ์คนสุดท้าย
- ทุกบทบาทและสิทธิ์เป็นต้นแบบในเบราว์เซอร์ ยังไม่มี backend/database หรือการบังคับสิทธิ์จากเซิร์ฟเวอร์ ไม่ใช้ข้อมูลจริง
- ทดสอบกฎรวม 27 กรณี และ TypeScript/production build 25 หน้า
- ตรวจ UI สมัครร้าน ส่งกลับแก้ไข ส่งใหม่ อนุมัติ เปิดขาย และตรวจบัญชี support ไม่เห็นข้อมูลเกินสิทธิ์แล้ว
- Phase 6 ที่เหลือ: ตรวจเส้นทางทั้งระบบและปรับประสบการณ์ก่อนเตรียมเชื่อม backend ตามแผนภายหลัง


## Phase 6 — ตรวจเส้นทางรวม (พร้อมทดลอง)
ตรวจสั่งอาหาร ส่งสลิปแก้ไข แชทข้ามแท็บ เปลี่ยนเมนูเพิ่ม/ลดราคา คืนส่วนต่างพร้อมหลักฐาน และรับอาหารด้วยรหัสครบแล้ว พร้อมแก้เส้นทางกลับจากล็อกอิน/แชท การซิงก์ตั้งค่าร้าน และการเลือกวันรับตามตารางร้าน

ผลตรวจและข้อจำกัดอยู่ใน [QA-PHASE-6.md](QA-PHASE-6.md) มี unit/integration tests 31 กรณี ตรวจ TypeScript, production build และลิงก์ภายใน static export ข้อมูลยังอยู่ในเบราว์เซอร์ ฐานข้อมูลและระบบสิทธิ์จริงเป็นงานขั้นต่อไปที่แยกจากต้นแบบนี้
